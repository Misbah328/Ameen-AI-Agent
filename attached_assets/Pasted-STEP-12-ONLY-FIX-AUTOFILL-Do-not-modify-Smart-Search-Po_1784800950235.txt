STEP 12 ONLY — FIX AUTOFILL

Do not modify Smart Search, Policies, Tasks, Meetings navigation, Dashboard Review Now, Boards, Members, Voting, or any previously completed fixes unless a shared autofill dependency makes a narrowly targeted change unavoidable.

==================================================
PROBLEM
==================================================

Autofill behavior is inconsistent or unreliable across forms.

Possible symptoms:

- Browser autofill does not populate fields
- Autofilled values appear visually but are not saved
- Autofilled fields do not trigger validation
- Reactivity or dependent fields do not update after autofill
- Autofill inserts data into the wrong field
- First name, last name, email, phone, company, or address fields are mismatched
- Password managers confuse unrelated fields
- Browser autofill overwrites existing form data unexpectedly
- Arabic and English fields receive the wrong value
- Form values disappear after re-render
- Autofilled values are not reflected in internal application state
- Submit button stays disabled even though all required fields are filled
- Validation errors remain visible after valid autofill
- Date, phone, email, organization, owner, or attendee values fail to persist
- Edit forms replace existing values with browser-stored values
- Mobile autofill behaves differently from desktop
- Chrome, Safari, Edge, or password managers behave inconsistently
- Hidden fields or duplicate names cause incorrect autofill mapping

==================================================
EXPECTED BEHAVIOR
==================================================

1. Forms must use correct semantic field attributes.

Where applicable, fields should include appropriate:

- name
- id
- type
- autocomplete
- inputmode
- aria-label or associated label
- required

2. Browser autofill must populate the intended field only.

Examples:

- Full name → name
- Given name → given-name
- Family name → family-name
- Email → email
- Phone → tel
- Organization → organization
- Job title → organization-title
- Address → street-address
- Country → country-name or country
- Username → username
- Current password → current-password
- New password → new-password
- One-time code → one-time-code

Use only values appropriate to the actual form.

3. Autofilled values must synchronize with application state.

The value shown in the input must be the same value used by:

- validation
- submit
- save
- dependent dropdowns
- preview
- API payload
- dirty-state detection

4. Autofill must trigger the same logical behavior as manual typing.

After autofill:

- required validation clears
- submit button state updates
- dependent values recalculate
- duplicate checks run if applicable
- formatting is applied safely
- no field remains internally empty

5. Existing edit data must take priority.

Opening an Edit form must not allow browser autofill to silently replace existing record data unless the user explicitly selects an autofill suggestion.

6. Autofill must not affect read-only or disabled fields.

7. Autofill must not populate hidden honeypot, search, filter, or unrelated fields.

8. Autofill must work in:

- English
- Arabic / RTL
- Desktop
- Tablet
- Mobile

9. Autofill must not create duplicate records or unintended writes.

==================================================
INVESTIGATION
==================================================

Inspect all forms that currently support user-entered identity or organization data, especially:

- Organization signup
- Login
- User or member creation
- Board member creation
- Attendee forms
- Profile or organization settings
- Meeting participant forms
- Policy owner or approver fields
- Any contact, email, phone, role, company, or address forms

Inspect:

- Field IDs
- Field names
- autocomplete attributes
- type attributes
- duplicate IDs
- duplicate name attributes
- labels and for attributes
- form wrappers
- input event handlers
- change event handlers
- validation functions
- form serialization
- save payload construction
- state objects
- render functions
- edit form population
- mobile and RTL variants
- password manager interaction
- hidden fields
- browser autofill CSS or animation hooks

Look specifically for:

- Missing name attributes
- Wrong autocomplete values
- autocomplete="off" used unnecessarily
- Same name used for unrelated inputs
- Input values read only from keyup events
- oninput not firing for browser autofill
- Controlled/uncontrolled field mismatch
- Validation only triggered on blur
- State initialized after autofill and overwriting the value
- innerHTML re-render replacing populated fields
- Edit form values assigned after browser autofill
- Hidden duplicate fields with matching names
- Search inputs incorrectly marked as email/name
- Password fields missing current-password/new-password distinctions
- Phone inputs using type="number"
- Arabic and English title fields sharing semantic autofill names
- Browser autofill styling hiding text
- Submit payload reading stale cached variables instead of DOM values

==================================================
IMPLEMENTATION REQUIREMENTS
==================================================

1. Audit first, then modify only actual autofill defects.

Do not add autocomplete attributes blindly to every field.

2. Correct semantic attributes.

Use:

- type="email" for email
- type="tel" for phone
- type="password" for passwords
- inputmode="email" where useful
- inputmode="tel" where useful
- appropriate autocomplete tokens

3. Every autofill-relevant field must have a stable and unique:

- id
- name

4. Do not reuse identity-related autocomplete tokens for unrelated business fields.

For example:

- Policy title must not use name
- Search field must not use email
- Board name must not use organization unless it truly represents an organization
- Arabic and English content fields must not both claim the same personal identity token

5. Synchronize autofill with application logic.

Use a robust approach consistent with the architecture:

- input and change listeners
- form-level value collection at submit time
- explicit state synchronization
- autofill detection only if genuinely necessary

Prefer reading final DOM values during save rather than relying exclusively on cached state.

6. If the browser applies autofill without firing expected events, implement a safe synchronization mechanism.

Possible methods:

- listen to input and change
- synchronize on focus, blur, submit, and visibility change
- compare DOM values before validation/save
- use CSS animation autofill detection only as a last resort

7. Validation must run against the current DOM values.

Do not validate stale state.

8. Edit-mode protection.

When editing an existing record:

- populate existing record data deterministically
- avoid clearing fields
- avoid delayed assignments that overwrite user input
- preserve user changes during re-render
- do not trigger unexpected autofill after opening

9. Login and password forms.

Use correct distinctions:

- username or email
- current-password
- new-password
- confirm password should normally use new-password
- avoid disabling password manager support unless there is a documented security reason

10. Phone fields.

Do not use type="number".

Preserve:

- leading +
- country code
- spaces
- hyphens
- leading zeroes

11. Arabic and English fields.

Content fields such as Arabic title and English title should generally use autocomplete="off" or a neutral value if browser identity autofill would be inappropriate.

Do not map both to personal name autofill.

12. Do not change visual design.

13. Do not alter existing database schemas unless absolutely necessary.

14. Do not implement Step 12 by disabling all autofill globally.

The purpose is correct autofill, not removal of autofill.
