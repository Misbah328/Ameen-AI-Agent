STEP 3 ONLY — FIX STALE OR INCORRECT DATA IN THE RESOLUTION VOTING MODAL

Do not modify meeting navigation, draft creation, sorting, calendar, dashboard, or any unrelated module.

Step 1 and Step 2 are already complete.

Your task is only to fix the Resolution Voting Modal so it always displays the data for the resolution the user actually clicked.

==================================================
PROBLEM
==================================================

The Resolution Voting Modal may show stale data from a previously opened resolution.

Example:

1. Open Resolution A.
2. Close the voting modal.
3. Open Resolution B.
4. The modal may still display Resolution A’s:
   - Title
   - Description
   - Resolution reference
   - Vote counts
   - Member vote statuses
   - Attachments
   - Deadline
   - Approval threshold
   - Previous voting result

This is a serious data-integrity and governance issue.

==================================================
EXPECTED BEHAVIOR
==================================================

Every time a user clicks Vote, View Voting, Review Votes, or Open Resolution:

- The exact clicked resolution ID must be passed.
- The modal must clear all previous data immediately.
- The system must load fresh data for that resolution.
- The modal must not reuse cached data from another resolution.
- Vote buttons must submit against the correct resolution ID.
- Vote counts must belong only to the selected resolution.
- Member statuses must belong only to the selected resolution.

==================================================
INVESTIGATION
==================================================

Inspect all resolution voting entry points, including:

- Resolution list
- Resolution detail page
- Circular Resolution list
- Dashboard widgets
- Notifications
- Global search
- Decision Registry, if it opens voting
- Direct URL or deep link
- Approval workflow pages

Search for stale state such as:

- currentResolutionId
- selectedResolution
- activeResolution
- votingResolution
- modalResolution
- cached resolution object
- localStorage
- sessionStorage
- global window variables
- reused DOM values
- delayed setTimeout callbacks
- unresolved async requests

Also inspect:

- Modal open function
- Modal close function
- Resolution API fetch
- Voting API submission
- Vote-results refresh
- Event listeners
- Re-render logic

==================================================
FIX REQUIREMENTS
==================================================

1. Pass the clicked resolution ID explicitly.

2. Before loading:
   - Clear title
   - Clear description
   - Clear vote counts
   - Clear member list
   - Clear attachments
   - Clear deadline
   - Clear status
   - Disable vote actions until fresh data loads

3. Fetch the selected resolution using its unique ID.

4. Confirm the API response ID matches the requested ID.

5. Prevent race conditions:
   - If Resolution A is loading and the user opens Resolution B, the response for A must not overwrite B.
   - Use a request token, request counter, AbortController, or equivalent safe method.

6. When the modal closes:
   - Clear selected resolution state
   - Remove temporary listeners
   - Clear loading and error states

7. Voting submission must use the currently selected resolution ID, not a stale global ID.

8. After a vote:
   - Refresh only the current resolution
   - Update the correct counts
   - Do not update another row or modal

==================================================
ERROR HANDLING
==================================================

If loading fails:

- Stop the loading spinner
- Show a clear error message
- Do not show old resolution data
- Provide Retry
- Keep voting disabled

If the resolution no longer exists:

- Show “Resolution not found”
- Do not fall back to a previously loaded resolution

If the user has no permission:

- Show a permission message
- Do not reveal restricted voting data
