STEP 11 ONLY — FIX SEARCH FOCUS

Do not modify Policies, Tasks, Meetings, Dashboard Review Now, Boards, Members, Voting, Autofill, or any previously completed fixes.

==================================================
PROBLEM
==================================================

The application search input has focus-related problems.

Possible symptoms:

- Search input loses focus while typing
- Typing one character causes the input to blur
- Search results re-render and move focus elsewhere
- Search works only after clicking the field repeatedly
- Search focus is lost after navigation
- Search focus is lost when filters or tabs update
- Opening or closing a result panel does not restore focus correctly
- Keyboard shortcut opens search, but the input is not focused
- Search input auto-focuses unexpectedly and interrupts other forms
- The cursor jumps to the beginning or end
- Search query disappears during re-render
- ESC clears the query but does not restore a usable state
- Search behaves differently in English and Arabic
- Mobile search cannot retain focus while typing
- Browser Back or Forward creates stale search focus

==================================================
EXPECTED BEHAVIOR
==================================================

1. Clicking the search input should focus it immediately.

2. Focus should remain in the search field while the user types.

3. Re-rendering search results must not replace or blur the active input unnecessarily.

4. The cursor position must remain stable while typing.

5. Existing search text must remain visible unless the user clears it.

6. The existing search keyboard shortcut, if supported, must:

- open or activate search
- focus the input
- place the cursor in a predictable position
- not trigger while the user is already typing in another input, textarea, select, or editable element unless intentionally designed

7. ESC behavior should be predictable:

- If a result dropdown or overlay is open, close it first
- If the query is present, clear it only if that matches the current product behavior
- Do not navigate away
- Do not leave an invisible overlay
- Do not trigger unrelated modal ESC handlers

8. When a search result is opened:

- Navigate to the correct record
- Close the search overlay if applicable
- Do not leave stale focus or backdrop
- Browser Back should return to a usable previous state

9. Search must not automatically steal focus when:

- a modal opens
- a form is being edited
- the user is typing in another field
- a dropdown or date picker is active
- the page first loads, unless auto-focus is an explicit existing requirement

10. Search must work in English, Arabic, desktop, tablet, and mobile layouts.

- asynchronous results from an older query replacing newer results
- ESC handler conflicts
- stale overlay remaining after navigation
- hidden search input retaining focus
- setTimeout focus hacks without cleanup
- cursor position reset because value is reassigned
- duplicate IDs
- mobile search element using a different implementation
- Arabic mode using a separate selector or DOM branch

==================================================
IMPLEMENTATION REQUIREMENTS
==================================================

1. Preserve the existing search input element whenever possible.

Do not recreate the input on every result render.

2. Keep search results in a separate container from the input.

Update only the results area when the query changes.

3. Preserve:

- input focus
- query text
- selectionStart
- selectionEnd

when a render is genuinely necessary.

4. Use one source of truth for the query.

Avoid separate unsynchronized values in:

- DOM
- global state
- module state
- URL state

5. If search is asynchronous, add race protection.

Only the latest query response may update the results.

Use a request sequence, AbortController, or equivalent architecture already used in the codebase.

6. Do not focus search automatically during normal page renders.

Focus only when:

- user clicks the input
- user activates the search shortcut
- user deliberately opens the search interface

7. Keyboard shortcut requirements:

- Support the existing shortcut only
- If both Ctrl+K and Cmd+K are expected, support both
- preventDefault only when the shortcut is actually handled
- ignore the shortcut when focus is inside an input, textarea, select, contenteditable element, or active modal unless the current product intentionally supports it

8. ESC requirements:

- close the topmost search dropdown or overlay
- preserve page state
- prevent conflicts with Policy and other modal ESC handlers
- remove stale listeners if search uses temporary listeners

9. On result selection:

- route to the exact result
- close search cleanly
- remove overlay
- reset temporary result state only if existing behavior requires it
- do not erase the search query before navigation unless intended

10. Focus restoration:

If search opens as a modal or overlay, save the opener and restore focus when search closes.

If search is an always-visible input, keep focus there after result updates.

11. Accessibility:

- Search input has an accessible label
- Results container uses appropriate listbox or list semantics if already compatible
- Active result is keyboard-reachable
- Arrow keys do not move page unexpectedly while navigating results
- Enter opens the highlighted result
- ESC closes results
- Focus indicator remains visible

12. Do not change the visual design.
